Behavior:
- fd_due(now, slot="auto", state=None) accepts the existing two arguments. slot no longer affects FD freshness; state is an optional receipt FILE Path. Missing file or no path is due; valid successful evidence suppresses collection for date differences 0 through 6 and becomes due at date difference 7. Both dates are UTC, not elapsed 168-hour windows.
- Optional state/fd_collection.json has exact schema {"version": 1, "last_successful_run_started_utc": "UTC ISO timestamp"}. It records the collect_apis(now) run-start anchor, written atomically only after a nonempty configured FD batch finishes complete. It does not claim a completion time, response capture time, or publication time. Raw captures are untouched.
- Download/parse failures, rejected rows, suspected duplicates, configuration failure, zero scope and receipt-write failure leave the previous successful receipt intact; partial batches never advance it. Other providers do not govern FD success. Normal manual/historical backfill does not write this receipt because it may cover a different subset.
- fd_due treats invalid/unreadable/future local evidence conservatively as due. Export and archive_info are deliberately stricter: exact schema, integer version 1 (bool rejected), full UTC ISO time, and no future run-start allowed. Export bounds against actual export time before archive mutation; archive_info bounds against manifest created_utc after hashes and before destination DB replacement. Corrupt published archives fail validation instead of silently discarding their evidence.
- Receipt is optional in old v1/v2 archives, included in the existing SHA256 state export/restore whitelist, and absent receipt on restore explicitly removes any newer local receipt. Existing receipt restores exact bytes. Thus a local successful collection followed by failed export cannot suppress collection after restoring the last published snapshot.
- FD configured scopes, import identity rules, other-provider windows, job slots, prediction triggers and technical-statistics schedule are unchanged. State contains no configuration fingerprint; existing normal weekly configured scope is the unit of successful collection.
