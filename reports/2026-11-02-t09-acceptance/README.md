## 取得真实数据后如何复核

从本分支运行，下例使用一个**新目录**；真实凭据只需由运行环境注入。没有 T08 真实库时不要用空库声称已核实去重率。

```bash
python examples/t09_capture.py --season 2026 --floor 2016 --output /tmp/t09-private-input
python examples/t09_replay_acceptance.py --capture /tmp/t09-private-input --baseline /path/to/t08.db \
  --season 2026 --since 2026-09-01 --as-of 2026-11-01T17:00:00Z --output /tmp/t09-private-result
```

`--floor` 是本轮主动探查的下限，不是账户可读的最早年；若下限仍返回有比赛的 200，须继续向前核实。当前季请求不带状态，历史季请求 FINISHED，每次查询单独记 HTTP、时间、原件哈希；403/404 边界与 200 空数组分开。持续 429 或传输错误时保留已得证据，不宣称整轮完成。若凭据仅在云环境的 setup 阶段可见，只在该阶段运行采集；随后用原件离线回放，勿复制密钥。

采集与回放可在不同环境运行。如果云端暂时没有 T08 基线，只需先收集原件、sidecar 和裁剪样本；把这些非凭据文件通过私有临时产物交给持有基线的验收环境。无需上传用户预测、数据库或密钥。云端使用 PR #11 的 head 分支 `codex/T09-football-data-org`，不依赖合并到 main。

回放以本源 ID 和整季赛程生成可审查别名，在基线的副本上导入，输出 `league_counts.json`、逐赛季审计和两组回测。在 `identity/coverage.json` 查看可比分母，在 `actual_unlinked.json` 核对**实际入库链接**遗漏的每一场。持续保留原始 UTC、SHA256、两端比赛 ID 和隔离原因。只在核验后更新正式别名及最早赛季；大文件不进 Git。
