## 发现

必须修

1. `src/zucai/stats_archive.py:43`（`check_stats`）——`match_stats.raw_value` 声明为 SQLAlchemy `JSON`，SQLite 对类型名
   `JSON` 采用 NUMERIC 亲和性，apif 的整数统计值（如 `corners` 的 `3`）会被存成 SQLite integer；`check_stats` 用
   `sqlite3` 读回后 `json.loads(3)` 抛 `TypeError`，被包装成 `ValueError("技术数据 JSON 字段无效")`。`check_db` 现在每次
   `export_feeds` / `restore_feeds` 都调用它，所以只要入过任何一场 apif statistics，**日常 apis 作业的导出就会失败**。
   SQLAlchemy 自身的 SQLite JSON 结果处理器会把数字原样放行，所以 ORM 路径没报错，测试没覆盖到。
   复现（离线 fixtures）：`tests/test_stats_storage.py` 的 `setup_link` + `save(tmp, "statistics")` →
   `ingest_apif(..., endpoint="statistics")` → `export_feeds(...)`，即抛上述错误；真实 72 份原件入库后同样失败。
   修法任选其一并补测试：(a) `check_stats` 对 JSON 列接受 `int`/`float` 为合法 JSON 标量；
   (b) 列改为 Text 并显式 `json.dumps`/`json.loads`，避免亲和性转换。
2. `tests/test_stats_storage.py:109`——导出 / 恢复测试只参数化了 `events / lineups / players`，恰好漏掉唯一有标量
   `raw_value` 的 `statistics`。请加入 `statistics`，并保证样本里含整数值与 `"56%"` 字符串值，防止回归。

建议修

3. `src/zucai/stats_command.py:fetch_index`——直接调用 `ApiFootball._request`（私有方法）并硬编码 `reserve=10`；建议在
   `ApiFootball` 暴露一个只读 `fetch_page(url)` 公开方法，`fetch_index` 调用它。不阻塞合并。
4. `check_stats` 对四表逐行 Python 校验（时间戳解析 + `json.loads`），T32 回填后四表合计约 300 万行，每次导出 / 恢复
   都要全量跑。建议 T32 任务单里要求改为 SQL 批量校验或抽样 + 行数哈希；本 PR 不改。

仅说明

5. 真实 fd 统计验收与 Actions 路径：T31 没有新增 workflow operation（任务单允许），因此 `stats ingest-fd` /
   `stats link --fetch` 现在都跑不进 Actions。T32 的 `stats-backfill` job 需要把这两步接进去，fd 的 2023/24–2026/27
   九联赛行数 / null 比例在那里验收。
6. 覆盖率前提：七个桥接联赛需要补 52 个 apif 球队 ID 的正式别名（候选表 `docs/aliases/2026-11-04-apif-bridging-leagues.md`）；库内 63 个 fd 英文原名球队已核对，仅荷甲 `Den Haag`（fd）与 `海牙`（jc、apif 198）是同一俱乐部的分裂身份，需补一条 fd 别名；其余沿用英文名不影响模型，
   否则 T32 回填只能覆盖约一半场次。审查者会按 T29 的流程另出一份候选表供所有者核准，不在 T31 内处理。
7. `red_cards` 等 apif 返回 null 的字段按规则保留 null（实际多为 0）；T33 做特征时应从 events 推导，不得把 null 当 0。
8. 四张技术表以 JSONL 全量进数据分支归档，T32 回填后单文件可达数百 MB；T32 任务单已定原件走 Release 附件，
   解析后行表的归档位置（分片 / 数据分支 / Release）需要在 T32 开工前定。
