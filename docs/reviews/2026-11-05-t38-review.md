## 发现

必须修

1. **审计 CSV 与行表的日增长不可持续。** 一天 11 页 ≈ 12 MB 明文进 `state/audit/injuries_ingest_audit.csv`，`cloud_feeds.STATE_FILE`
   把它纳入数据分支提交，一年约 4 GB 进 git 历史，所有 job `fetch-depth: 0` 检出。95% 的 `unresolved` 来自没有 fixture index 的
   美职 / 挪超 / 瑞超 / 丹超 / 澳超；`snapshot` 对每个 fixture 每天重写完整名单。`match_injuries` 以 `captured_day` 入唯一键，
   同一条目每天新增一行（≈ 410 万行/年）。要求：(a) 行表按内容变化记版本（首次 / 末次捕获区间），未变不新增；
   (b) 逐条 `unresolved` 与逐 fixture `snapshot` 不每天追加到 git 跟踪的 CSV：无 index 的联赛只记每页计数，快照只在该 fixture
   条目集合有变化时写（特征按最近一次快照前推），或放进压缩的按次捕获文件随 `stats-raw-YYYYMM` Release 发布；
   (c) PR 给出修改后同一 11 页回放的 CSV 字节与行数（目标 ≤ 300 KB/天）。
2. **实验只评 strict 目标，历史上必然 n=0。** 所有伤停与统计都是 2026-11 才捕获，2025/26 目标在 strict 下永远拒绝，补回
   2022–2025 季页也不改变这一点。任务单第 3 条要求两种口径、第 4 条要求回答「是否更准」。请在协议中加入 `backfill_replay`
   目标口径作为第二张表（假设「最近归档名单在开球前已知」并显式标注），strict 表保留为诚实的零；两表分列不混算。
   当前结果全为 null，属「结果前修正协议」。

建议修

4. 合入时机：technical_data 升到 v3 后，若一个仍在跑的旧代码作业随后发布 v2，会丢掉伤停分片。合并避开 02:40 / 09:40 UTC
