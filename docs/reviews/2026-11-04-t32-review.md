## 发现

必须修

1. `.github/workflows/football-feeds.yml:461`——`sporttery` job 跑在 Windows 自建 runner，默认 shell 是 pwsh；新增的
   「Validate dispatch options」步骤没有 `shell: bash`，脚本是 bash heredoc（`python - <<'PYOPTIONS'`），pwsh 会在
   `<<` 处解析失败。该步骤只在 `workflow_dispatch` 运行，所以定时任务不受影响，但手动 `operation=sync` 会在真正工作前失败。
   该 job 根本不读 `options`，建议直接删掉这一步；若保留则加 `shell: bash`（同 job 其他步骤的做法）。

建议修

2. `src/zucai/stats_rows.py:283` 与 `stats_batch.py:329`——同一批次里 `restore_rows` 已把全部历史分片下载、校验并装回暂存库
   （含 snapshot 哈希核对），随后 `publish_rows` 又 `_download_shards(previous)` 把全部历史再下载一遍做 `verify_only`。
   目前体量小无妨，但每批两次全量下载随历史线性增长（22,075 场约数百 MB 压缩）。建议 `collect_batch` 把「本批已完整装回并核对」
   传给 `publish_rows`，跳过第二次下载；或把 verify 限定为本批触及的联赛季分片。
3. 每次发布都对全部历史重新压缩分片（文件名含内容哈希，未变的分片靠 Release 同名同哈希短路，不重复上传）。
   当前可接受；T33 前若日常步骤时长明显增加，再改为按联赛季增量分片。写入 T33 前置观察项即可。

仅说明

4. **切换顺序**：T31 main 不读 v2，T32 普通导出不丢弃未发布的 v1 行表。审查者建议**先合入 T32，再在 main 上做真实验收**：
   合入后第一次晚班 `apis` 会用 T32 代码导出 v2（0 行或日常新增行），之后 `stats-backfill` 随时可跑；
   不在分支上先跑真实回填，避免 main 的定时任务在合入前读到 v2 失败。合入时机选在 09:40 UTC 定时任务结束之后。
5. `refresh_context` 用普通采集已归档的 fixtures 页为 11 个 apif 采集联赛建索引（不发新请求），索引范围因此覆盖 18 个联赛；
   索引**请求**仍只有七桥接＋欧冠。与研究笔记 22,075 场预算口径一致，文档已写明「复用已采集 fixtures 原件刷新索引」。
6. `injuries` 只留原件与覆盖率，T31 没有 injuries 表；T33 若要用伤停需先建表。
7. 新依赖 `zstandard`（纯压缩库，非重型依赖）。
8. 晚班 `cloud_stats daily` 步骤 `continue-on-error: true`，归档失败只发布配额与错误记录，不阻断普通 feeds 发布；
   成功时由 `_adopt` 原子替换归档再统一推送。
