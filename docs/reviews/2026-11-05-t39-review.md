## 必须修

1. **赛程阶段失败后 `sporttery_stale` 失真。** `cloud_feeds.collect_jc` 把赛程 / 赛果失败都收成 `status=partial`，job 本身成功；
   `cloud_feeds` 只在赛果窗口不完整时把 `through_beijing` 退回上一日，赛程失败时仍写当日
   （`tests/test_cloud_feeds.py::test_schedule_and_results_success_times_are_separate…` 对 `failed_stage="schedule"` 断言 `through_beijing == 当日`）。
   而 `cloud_predict.run` 的 `sporttery_stale = sporttery_status != "success" or through_beijing != 当日`：改前赛程抓取失败会让 job 失败、
   `sporttery_status=failure`，预测摘要写「竞彩数据非今日」；改后同一情形 job 成功、水位为当日，`sporttery_stale=False`，
   预测摘要与 `forecast_manifest` 都把旧赛程 / 旧赔率当成今日数据。复现：用该测试的 `schedule` 分支导出归档后跑 `cloud_predict.run(sporttery_status="success")`。
   修法任选其一：`cloud_predict.run` 另读 `feed["collection"]["jc"].get("schedule_status", "complete") != "complete"` 计入 stale；
   或 sync 在赛程阶段失败时仍发布 partial 但以非零退出码结束（现有 `!cancelled()` 链路不受影响）。补一条测试。

## 建议修

1. **头部失败措辞区分阶段。** `digest_views.header_lines` 只要 `failed_stages` 非空或任一阶段为 `failed`/`partial` 就写
   「赛果更新失败（run …），还有 N 场已开球未核对」。赛程失败、赛果失败、赛果 `partial`（页面都读到了，只是部分赛果还没出）三种情形
   措辞应不同：赛程失败写「赛程更新失败」；赛果 partial 写「赛果部分未到，还有 N 场待核对」，不叫失败。所有者原话是「同步失败就写…」。
2. **完整清单按月分片。** `state/audit/jc_catalog.csv` 每次同步追加原响应全部编号（每行约 150 字节），每天 2–3 次同步、每次数十行，
   一年约 5–10 MB，且 `digest_context.audit_rows` 每次日报整文件读入。建议与 `state/odds/<YYYY-MM>.jsonl` 一样按采集月份分片
   （`state/audit/jc_catalog/<YYYY-MM>.csv`），`export_feeds` 的审计正则同步放宽；`jc_skipped.csv` 同理。可作为合入后的小修。

## 仅说明

1. **存好时间取提交时间而非服务器接收时间。** `%cI` 是 runner 本地提交时刻，比 push 到达早几秒；Git 不提供服务器接收日志，
   PR 已说明。误差方向是「偏早」，极端情况（提交 17:29:58、push 17:30:02）会把实际 17:30 后才可查的报告判为赶上。可接受，记录在此。
2. **通知回执依赖 GitHub 返回正文逐字一致。** `digest_notify._record_notification` 若响应 `body` 与冻结正文不同即抛错，step 失败，
   下一版会退化为「本日首版」。GitHub 目前原样返回评论正文，仅提示该假设。
3. **每版日报三份正文。** `daily/<日>.md`、`daily/latest.md`、`daily/<日>/<run>.md` 内容相同，每天 2–3 版、每版约 65 KB；
   git 存差分，数据分支增长可接受。
