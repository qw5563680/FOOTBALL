来源：2026-11-12 独立复核（ChatGPT）问题 3，审查者在代码中确认机制；外加 T52 审查（PR #106）两条建议修。

## 一、复盘必须选「开球前已发布」的版本（主项）

### 现象与证据

- `src/zucai/scoreboard/score.py`：`prematch_rows` 只要求 `as_of_utc <= generated_utc < kickoff_utc`；
  `summarize_scores` 按 `generated_utc` 排序取每场最后一条。全程不比较「预测推送到数据分支、用户能看到」的时间。
- `forecast_manifest.json` 的 `runs[*].forecasts[day]` 只有 `generated_utc`，没有正式预测的发布时间字段
  （仅实验预测有 `experimental_published_utc`）。
- 复核实例：2026-11-07 run 42380973719，4 场德甲在北京 22:28 算完、22:30 开球、22:34 才发布；
  复盘选中了这份用户开球前看不到的版本。复核员称换回赛前已发布的上一版后正式概率相同、
  正式命中不变，但 xG 实验可比样本从 31 变 35。审查者只在代码中确认了机制，未端到端复跑。

### 范围

- 发布时为每个正式预测批次记录发布时间（例如 `published_utc`，取数据分支推送成功后的时间）。
- 复盘、记分板、纸面账户、实验对照选版本时，要求 `published_utc < kickoff_utc`；不满足的版本不进入
  有效记录，并在审计中按原因计数（如 `published_after_kickoff`）。
- 历史批次没有该字段时：从数据分支首次包含该文件的提交时间推导；推导不出则标为「发布时间未知」，
  单独计数、不得当作赛前已发布。规则需写进 ARCHITECTURE。
- 记分板展示：因发布晚于开球被排除的记录数、发布时间未知的记录数。

### 不做

不改模型、参数、BET；不回写已冻结预测、旧评分或旧账本文件（新口径在读取时重新选取）；不使用正式 key。

### 验收

1. 用数据分支固定快照离线重放 2026-11-07：上述 4 场德甲不再选 run 42380973719 的版本，改选赛前已发布的上一版；
   报告这 4 场正式概率与命中是否变化（如实写，不预设结论）。
2. 构造「生成早于开球、发布晚于开球」与「发布时间未知」两种记录：均不进入有效复盘，且分别计数。
3. 发布时间早于开球的既有记录，选版本结果与修改前逐字节一致。
4. 重放前后全部归档文件 SHA256 不变；全量 pytest、ruff 通过。

## 二、T52 遗留小修（附带）

### 1. 竞彩开售后的窄窗口回退

`src/zucai/sources/sfc.py` `refresh_snapshot` 中欧国联行「存档 `match_id` 与刷新候选不同即判 `ambiguous / 期次原场次待复核`」的守卫，
在 T52 回退后有一个窄窗口：存档行是回退得到的 apif 比赛，竞彩开售后 jc 比赛入库、但期次未被重新入库时，
候选变为 jc 比赛，6 场会再次掉出预测。审查者已离线复现（见 `docs/reviews/2026-11-12-t52-review.md`）。

- 范围：当候选 jc 比赛的 `counterpart_id` 正是存档的 apif 比赛（或反之）时视为同一场，不判歧义。
- 验收：补「目标以正确身份后来出现、且期次未重新入库」回归测试，刷新后仍 matched；
  主客颠倒等错误身份仍拒绝（现有 `test_dead_bridge_is_checked_again_if_target_later_appears` 保持通过）。

### 2. 日报提示的映射计数与 14 场栏矛盾

`src/zucai/digest_views.py` `_known_unstarted_lines` 的「未映射 N 场、已映射 M 场」取自原始快照，
修复生效后会与下方 14 场栏的有概率场数互相矛盾。

- 范围：改用刷新后的映射状态，或只写「N 场未在本表展示，见下方 14 场胜负彩」而不报映射计数。
- 验收：用 26163 期真实快照重放，提示中的计数与 14 场栏一致（或不再出现计数）。
