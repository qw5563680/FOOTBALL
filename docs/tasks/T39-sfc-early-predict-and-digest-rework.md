# T39 · 14 场提前预测、每日报告重排与竞彩编号对齐

## 背景
2026-11-04/05 的每日报告（Issue #39）暴露了四类问题，所有者 2026-11-05 逐条拍板如下，本任务单据此起草：
1. **14 场胜负彩永远「无模型」**：期次 26158 的停售时间是 11-04 17:30（北京），而预测在 17:40 晚班才生成，T35 的冻结条件在时间上
   永远赶不上；赶不上时报告仍把 14 场逐行列成「无模型 / 复式 3+1+0」，容易被误读成模型给出的全选结论。
2. **报告时间与内容不符**：11-04 晚班的定时任务被 GitHub 推迟到 11-05 01:28 才跑，又因旧代码的 GBK 问题竞彩同步失败，于是 01:39 发出的
   「2026-11-05 报告」写着「昨日无已结算场次」、虚拟账户 8 注欧冠全部「待结」，其中 4 注（巴萨–维拉、博德–里尔、比利亚雷–巴黎、LASK–布拉迪斯）
   早在 11-04 04:00 开球并踢完，另 4 注（维京–萨巴赫、费内–利物浦、朗斯–科莫、莱红牛–曼城）当时确实未开球。报告没有区分这两种「待结」，
   也没有写明赛程和赛果各更新到几点。
3. **「今日预测」被已开赛比赛淹没**：11-04 报告的「今日」一栏 10 行全是「未预测：预测截点时已开赛」。
4. **竞彩编号不齐**：周三 001–011 里缺 003，012 也不在单场表。原因：`sources/sporttery.py::parse` 只保留同步时刻
   `matchStatus=Selling` 且有固定奖金玩法在售的比赛；11-04 唯一成功的竞彩同步是 11:30（run 41767507843），当时 003 / 012 尚未开售
   （晚班同步失败）；原件也没有归档，无法事后核对它们是哪两场。同期 14 场里「加的夫–西汉姆联、布里斯托尔城–伍尔弗（英联杯）、
   雷克斯汉姆–米德尔斯堡（英冠）、弗拉门戈–格雷米奥（巴甲）」四场在库内不存在，与缺号一致，但只是推断。
5. 虚拟账户 D「累计 ROI −100%」只投了一注，口径没错但缺投入与盈亏，读起来吓人。

## 目标
1. 有 14 场期次的日子增加一次 **15:40（北京）** 的提前预测，保留 17:40 晚班；冻结报告必须在停售前存好，赶不上就写明「本期错过停售」，
   任何情况下不把「3+1+0 全选」显示成模型结果。
2. 每日报告重排：开头写清竞彩**赛程**与**赛果**分别更新到几点；同步失败写「赛果更新失败，还有 N 场待核对」；
   「今日预测」只放未开赛比赛，已开赛的进「复盘」区并保留最后一次有效赛前预测；按竞彩编号列齐并解释缺号；
   复盘首行「已结 X 场、猜对 Y 场、猜错 Z 场」；虚拟账户把投入、盈亏、回报率放在一起。
3. 竞彩编号缺失可解释：同步时记录被跳过的比赛及原因，原件归档为 Actions artifact。

## 范围
1. **提前预测（workflow + `cloud_predict`）**
   - `football-feeds.yml` 新增 cron `40 7 * * *`（北京 15:40）。该班次只在「存在当日或次日停售的 14 场期次」时执行 sporttery 同步 + predict + scoreboard + digest，
     否则在第一步判定后直接结束（不发体育 API 请求）。判定依据：`state/sfc/<issue>.json` 的停售时间；无法判定时视为有期次（宁多跑不漏）。
   - 17:40 晚班照旧；同日两批预测各自成目录，不覆盖（现有规则）。记分板「最后一次有效赛前预测」规则不变。
   - `sfc_reports` 冻结条件以**存好时间**为准，不以算完时间为准（所有者 2026-11-05 第二次拍板）。每份冻结报告同时记录两个时刻：
     `generated_utc`（算完：概率生成完成）与 `published_utc`（存好：报告已推送到数据分支、可以查到的时刻，取发布该文件的数据分支提交时间）。
     只有 `published_utc` < 停售时间才算「赶上停售」；`published_utc` ≥ 停售时间即 `missed_deadline`，摘要写
     「本期错过停售（停售 HH:MM，算完 HH:MM，存好 HH:MM）」。例：17:29 算完、17:30 停售、17:32 才存好，本期必须显示「错过停售」。
     查不到 `published_utc`（发布失败、只在 artifact、提交时间缺失）时状态为 `deadline_unconfirmed`，摘要写「无法确认赶上停售（算完 HH:MM，存好时间未知）」。
     `missed_deadline` 与 `deadline_unconfirmed` 两种状态都只显示对阵与「无冻结概率」，**不再显示 3+1+0 复式列**；已确认赶上的期次照常显示。
   - 验收口径：以 `state/sfc/<issue>.json` 的停售时间与报告的 `published_utc` 比较；`generated_utc`、`published_utc`、停售时间三者都写进报告、
     `manifest.json` 与 Actions 摘要。predict job 的发布步骤要把发布提交哈希与时间回写到当次报告的 manifest（或由 digest 从数据分支
     `git log` 读取该文件的首次提交时间），不能用「算完时间」冒充「存好时间」。
2. **每日报告（`daily_digest.py`）**
   - 头部新增两行：「竞彩赛程更新至：<最近一次成功 jc 同步的 UTC→北京时间>」「赛果更新至：<最近一次成功赛果核对时间>」；
     任一失败写「赛果更新失败（run <id>），还有 N 场已开球未核对」，N 按「已开球且无赛果的本周冻结预测场次」计算。
   - 「今日预测」只列生成时刻之后开球的比赛；已开球或已结束的进新节「复盘」，每场保留最后一次有效赛前预测（记分板 active_keys 口径）、
     实际比分（无则「待核对」）、首项是否命中；复盘首行固定「已结 X 场、猜对 Y 场、猜错 Z 场、待核对 W 场」。
   - 两节都按竞彩编号（`jc_num`，如 周三003）排序并列齐。缺号要区分两件事并分别写明：**「确定漏了」**（当期竞彩完整清单里有这个编号，
     但本报告的预测表里没有）与**「知道为什么漏」**（第 3 条的跳过审计给出了原因）。缺号行格式：
     「缺 周三003：确定漏了；原因未查明（早班原始页面未归档）」「缺 周三012：确定漏了；晚班同步已入库，但无可查的赛前预测」。
     判定「确定漏了」必须依据第 3 条归档的**当期完整清单**逐号核对，不能只看编号序列是否连续——像 012 这样排在末尾的编号，
     光看 001 到 011 是发现不了的。没有当期完整清单（旧归档）时写「无法判定是否漏号（无当期完整清单）」。
   - 虚拟账户表改为「已结 N 注，投入 X，盈亏 ±Y，回报率 Z%」，待结注单单列并区分两类：「发报时未开球」与「发报时已开球、赛果尚未核对」。
     分类**以本版日报的生成时刻**（digest 的 `generated_utc`）与每注最早一腿的开球时间比较，不用注单生成时刻、不用上一版的时刻。
   - 每一版日报都要让人看懂「当时知道什么、后来补回什么」：在虚拟账户节（或复盘节）加「较上一版」小段，列出上一版仍待结、本版已结算的注单
     汇总，格式如「上一版待结 8 注（4 注未开球、4 注已开球未核对）→ 本版已结 8 注：1 中 7 错，盈亏 −680」。上一版的待结集合取同一 Issue
     评论的前一版归档（`daily/<日期>/<run>.json` 或等价的冻结摘要数据），没有上一版时写「本日首版」。
   - 同日第二班（15:40 之后的 17:40）照常编辑同一条评论；编辑后头部要写「本日第 k 次更新」。
3. **竞彩同步可解释（`sources/sporttery.py`）**
   - `parse` 对未保留的比赛写一条跳过记录：`jc_num`、`matchId`、`matchStatus`、`sellStatus`、是否有固定奖金玩法、对阵与联赛；
     写入 `state/audit/jc_skipped.csv`（幂等、按同步时刻去重）。
   - 每次同步另存**当期完整清单** `state/audit/jc_catalog.csv`：原始响应里每个营业日的全部编号（含未在售、已停售的），字段
     `business_date`、`jc_num`、`matchId`、对阵、联赛、`matchStatus`、`sellStatus`、本次是否保留、同步时刻；按（营业日、编号、同步时刻）去重。
     第 2 条的缺号判定只能依据这份清单逐号核对。
   - sporttery job 把当次原件（已存在的 `data/raw/sporttery/...`）作为 Actions artifact `sporttery-source-<run>` 上传（90 天），与 apis 一致。
4. **文档**：README「每日摘要」「14 场」两节、ARCHITECTURE 相应小节、workflow 说明。

## 测试（离线）
停售时间 vs 存好时间的三例：存好早于停售（冻结）、算完早于停售但存好晚于停售（`missed_deadline`，不输出复式列）、
存好时间缺失（`deadline_unconfirmed`，不输出复式列）；提前班次判定（有期次 / 无期次 / 无法判定）；
摘要头部两行与失败措辞；今日 / 复盘拆分与最后一次有效预测；缺号行的「确定漏了 / 原因未查明 / 入库但无赛前预测 / 无法判定」四种措辞；
复盘首行计数；账户三要素；待结注单按本版生成时刻拆成两类；「较上一版」汇总（有上一版 / 本日首版）；
跳过审计与完整清单幂等；旧归档（无 `jc_skipped.csv` / `jc_catalog.csv`）照常生成并写「无法判定」。

## 验收标准（所有者 2026-11-05 拍板，PR 必须逐条对照）
1. **赶上停售只看存好时间。** 报告与 manifest 同时有算完时间和存好时间；存好时间晚于停售即「错过停售」（17:29 算完、17:30 停售、17:32 存好 → 错过）；
   查不到存好时间写「无法确认赶上停售」；两种情况都没有 3+1+0 复式列。
2. **待结注单按发报时刻分类，并写清补回情况。** 以 11-05 01:39 那版为例：8 注里 4 注发报时未开球、4 注已开球但未核对赛果，报告要这样分开写；
   晚班更新后那一版要写明这 8 注最终「1 中 7 错」，并有「较上一版」小段让人看懂当时知道什么、后来补回什么。用真实归档离线重放这两版作为 PR 样例。
3. **缺号区分「确定漏了」和「知道为什么漏」。** 周三003 在所有者截图里有、早班原始页面未归档，缺号行写「确定漏了；原因未查明」；
   周三012 后来进了晚班表但无可查的赛前预测，缺号行两件事都写。以后有当期完整清单（`jc_catalog.csv`）就逐号核对，末尾编号也不能漏。
