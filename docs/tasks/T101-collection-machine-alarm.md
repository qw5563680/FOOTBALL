# T101 采集机上的定时闹钟：到点由采集机去叫醒自动保险检查，不再只靠 GitHub 的定时

来源：所有者 2026-11-27「写，两个都写」。稳定性问题，排在功能之前。

## 现状（main `aa0695d`）

- 每日链路靠 GitHub 的定时启动（UTC 02:40、07:40、09:40 三档）。T85（#254）加了自动保险检查 `football-watchdog.yml`：
  UTC 03:05、03:35、08:05、08:35、10:05、10:35 各检查一次，本档没跑就补一班。
- 2026-11-27 实际情况：GitHub 的定时全天一次都没有发出来。每日链路的两档没有启动，**自动保险检查自己的六个时间点也一次都没有启动**
  （`football-watchdog.yml` 自合并以来运行次数为 0）。当天的 5 班全部是 Claude 手动触发的。
- 也就是说，T85 是用 GitHub 的定时去检查 GitHub 的定时：GitHub 定时不灵时它一起不灵。Claude 停工时没有任何东西会补跑。
- 自动保险检查本身支持手动触发（`workflow_dispatch`），被触发时会按当前时间判断是哪一档、要不要补（`src/zucai/watchdog.py` 的 `_slot`）。缺的只是一个 GitHub 以外的闹钟。
- 采集机（所有者的 Windows 电脑）本来就必须开机在线，每日链路的 `sporttery` 环节才跑得了。它现在用「非管理员、用户登录时触发的计划任务」运行 GitHub 运行器（`docs/RUNNER.md` 方式 A）。

## 范围

1. **采集机上加一个计划任务**，在北京时间 11:05、11:35、16:05、16:35、18:05、18:35（即上面六个 UTC 时间点）各触发一次自动保险检查
   `football-watchdog.yml`。只做「叫醒」这一件事：要不要补跑、补哪一档，仍由自动保险检查按现有规则判断。不直接触发每日链路。
2. **只用 Windows 自带的东西**（PowerShell 与任务计划程序），不依赖工作流临时安装的 Python，不安装新软件。脚本放进仓库，
   由所有者按说明在采集机上安装一次；以后脚本有更新，也要所有者自己重新安装才生效，程序不自动更新自己。
3. **触发需要一个 GitHub 令牌，由所有者自己创建并只留在采集机上。**
   - 用细粒度令牌：只对本仓库有效，权限只开「Actions：读写」，其余全部不开；有效期由所有者选，说明里建议不超过一年。
   - 安装脚本在采集机本地提示所有者粘贴令牌（沿用 `docs/RUNNER.md` 里 `Read-Host` 的做法），用 Windows 自带的方式加密保存，
     只有所有者这个 Windows 账号读得出来。令牌不进仓库、不进日志、不进任何输出，也不交给任何 AI 会话。
   - 这是采集机上新增的一份凭据，与「数据接口的正式 key 只放在 GitHub Secrets」那条规矩不是一回事，但同样要所有者点头：合并本任务单即表示同意。
4. **给采集机上的东西加保护**（所有者的既定要求）：
   - 脚本只向 `api.github.com` 发请求，只调用两个地址：读本仓库 `football-watchdog.yml` 的最近运行、触发它一次；不下载、不执行任何别的内容；
   - 每次触发前先看最近 20 分钟内是否已有一次自动保险检查在跑或刚跑完，有就不重复触发；每天最多触发 6 次；
   - 请求失败、令牌失效或过期时，写一行日志后退出，不重试轰炸，不弹窗；
   - 日志只写时间、结果和 HTTP 状态码，文件大小有上限，超过就截断；
   - 脚本文件里不直接写中文（#241 的教训）；提供一条卸载命令，卸载后计划任务、令牌文件和日志都删干净。
5. **让所有者看得见闹钟还在不在工作。** 日报顶部加一行：最近一次自动保险检查的运行时间和是谁触发的（GitHub 定时 / 采集机闹钟 / 手动）。
   本档一次都没有运行时写明「本档自动保险检查没有运行」。数据只从 Actions 的运行记录里读，读不到时照实写「未能读取」，不影响日报其余部分。
6. `docs/RUNNER.md` 增加「采集机闹钟」一节：安装、检查、更换令牌、停用、卸载，逐步写清，所有者照着做得下来。`README.md`、`docs/ARCHITECTURE.md` 同步。

## 不做

- 不改每日链路的三档时间和自动保险检查的判断规则；不删除 GitHub 的定时（它正常时照旧工作）。
- 不让采集机直接触发每日链路、探测或任何别的工作流；令牌权限不超过「Actions：读写」。
- 不把令牌写进仓库、GitHub Secrets 以外的任何云端位置、聊天或 PR。
- 不引入第三方定时服务，不新购服务。
- 不解决「采集机关机或断网」的情况：那时每日链路本来就跑不了。日报那一行会让所有者看见闹钟没响。
- 不停用 Claude 的定时保险检查；是否停用等本任务单验收后由所有者决定。

## 验收标准

1. 离线测试（GitHub 的 Linux 检查环境里有 PowerShell）：最近 20 分钟已有运行时不触发；没有时只触发一次；当天满 6 次后不再触发。
2. 离线测试：令牌缺失、失效（401）、接口失败时，各写一行日志并正常退出；日志和任何输出里没有令牌内容。
3. 离线测试：脚本只出现 `api.github.com` 上述两个地址；脚本文件是纯 ASCII；`tests/test_windows_collection_machine.py` 通过。
4. 离线测试：日报那一行在「GitHub 定时触发」「采集机闹钟触发」「手动触发」「本档没有运行」「未能读取」五种情况下文字正确。
5. 安装与卸载说明经审查者逐步核对；卸载后计划任务、令牌文件、日志都不存在。
6. 合并后：
   - 所有者按 `docs/RUNNER.md` 在采集机上安装一次（Claude 把步骤用大白话列给所有者）；
   - Claude 观察三天：每个时间点前后 10 分钟内都有一次由采集机触发的自动保险检查；GitHub 定时没发的档由它补上，整条链成功；
     日报那一行与实际运行记录一致。三天达标后发回执，T85 与本任务单一并验收。
