   结论为 `duplicate` 的条目，即使之后对照获批、两支球队已经合并，仍然永远是 `pending`。所有者批准了接口绑定的球队（比尔森、比亚韦）同样不会出队。
2. **处置计划很容易作废。** 计划要写明整个身份清单和整个队列的哈希（`inventory_sha256`、`queue_sha256`），执行时两者必须与当时的归档完全一致
   （`jc_candidate_review.py` 的 `apply`）。每天三班采集都会改动身份清单，计划写好到审查者触发之间只要跑过一班就作废，要重新来。
   至今只成功执行过一次（`data/jc_candidate_reviews/2026-11-13-first-five.json`）。

   看不出哪条在等所有者批准、哪条在等审查者处置、哪条已经处理过但没出队。

## 范围

1. **有依据的条目自动出队。** 每班采集后复核待核条目，满足下面任一条就出队，并在条目里写明依据和时间，不需要处置计划：
   - 该条目的球队行已经带有正式别名表里**获批**的接口绑定（`approved`，含批准人与批准 PR）；
   - 该条目的队名在竞彩别名表或 fd 别名表里已有**获批**的对照，并且对照指向的球队就是该条目现在所属的球队行（即两支球队已经合并完成）。
   - 只凭 `auto_verified`、名称相同或相似、或者「没有冲突」都不算依据，这类条目继续待核。
   - 出队写新的状态值（例如 `resolved`），与人工处置的 `cleared` 区分开；旧条目照常可读。
2. **处置计划只和它涉及的内容绑定。** 计划里每条决定绑定它实际依赖的事实：该候选条目本身、它核对过的球队行、用作证据的比赛。
   这些没有变化时，别处的每日变化不让计划作废；这些有变化时照旧停下来要求重新核验。现有的逐条检查（`_decision`）不放宽。
   已归档的旧计划和旧审计照常可读。
3. **日报写明待办。** 待核条目全部列出，不再只列 5 个；每条写明处在哪一步，至少区分：
   「从未处置」「处置结论是重复，等所有者批准对照」「处置结论是未决」。条目总数与逐条数量一致。本班自动出队的条目列一次，写明依据。
4. `README.md` 与 `docs/ARCHITECTURE.md` 同步。
