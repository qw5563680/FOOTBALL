# T78 14 场名单自带赛程：没有赛程来源的场次也出预测

来源：所有者 2026-11-19 的两句话——
「不管竞彩有没有开十四场的比赛，你都得把这两个拆开去，根据大模型，给出正常的预测」；
「先做第四点，再完成法乙比赛的数据收集进模型，再把名字没有对上的比赛完成」。

## 问题

PR #212 之后，轮到的那一期里「对上了库内比赛」的场次都出预测。但有的联赛库里根本没有赛程：
法乙的历史赛果来自 football-data.co.uk，它只在赛后给赛果；竞彩卖的法乙比赛有赛程，竞彩不卖的没有。
26166 期第 6–10 场（5 场法乙）因此「未映射」，没有预测。

模型做一场预测只需要四样东西：联赛、主队、客队、开球时间。14 场名单本身就印着这四样。

## 范围

1. **名单自带赛程。** 采集期次时（`collect_current_sfc`），某一行同时满足下面几条，就以这一行本身建一条赛程
   （`matches.source = 'c500'`，`match_id = 'c500:<来源场次编号>'`，沿用项目早先本地流程的既有约定）：
   - 竞彩没有卖这一场（没有编号对照）；
   - 库里没有这场比赛（按联赛、主客队、开球时间找不到任何来源的记录）；
   - 两队都是库内已有的球队（队名完全一致，或 `data/team_aliases/sfc_clubs.json` 里所有者批准的简称），
     而且两队在这个联赛里都已经有比赛记录；
   - 不是欧国联（国家队走原有通道）；开球时间不是占位时间。
   不新建球队、不改队名、不加别名。任何一条不满足，这一行照旧「未映射」。
2. **再读名单时只用不写。** 预测、报告各步重读期次快照（`refresh_snapshot`）时，认已存在的自带赛程，自己不建。
3. **正规来源优先。** 之后竞彩开售，或者接口有了这场赛程，映射自动改到那一条；自带赛程留在库里不再使用。
4. **来源改了开球时间。** 采集时跟着改；两次采集之间重读发现不一致，按身份冲突处理，该行不出预测。
5. **模型怎么找。** 单联赛模型除了自己训练来源的比赛，也可以预测本联赛的自带赛程
   （`zucai.predict.base.fixture_sources`）。欧战合并模型不适用。自带赛程没有赛果、统计和赔率，永远不进训练。
6. **照实标注。** 映射依据记 `sfc_own_fixture`；14 场报告和日报在表下各加一行，写明哪几场的对阵与开球时间取自期次来源本身（第三方）。
   这些场次沿用 `sfc_only` 通道：不进虚拟账户与纸面串关，日报的竞彩表不列。
7. **一条简称。** `sfc_clubs.json` 增加法乙「圣红星」＝圣旺红星（来源球队编号 6597），须所有者批准。
8. 同一个 PR 里的另一处改动：Release 读写遇到连接中断时重试（见下「附带修复」）。

## 不做

- 不接入新的赛程接口（法乙的 API-Football 路线仍是候选，另行立单）。
- 不改任何模型的拟合、参数、训练来源和既有预测概率。
- 不把自带赛程的赛后结果接进通用记分；14 场的命中仍按期次自己的结算口径统计。
- 不读取赔率或任何市场信息；BET 保持禁用。

上传中断时重做整个受校验的流程（先重新列附件，已到达的按文件名、大小、哈希认出来，不重复发送；同名不同哈希仍然拒绝，不覆盖、不删除）；
收到任何 HTTP 状态码的回答都不重试。失败时运行日志多一行错误类型（只写类名）。
