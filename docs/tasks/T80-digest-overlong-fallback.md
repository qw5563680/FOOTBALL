# T80 日报太长时也要发出去

来源：所有者 2026-11-25「交给 Codex 修」；`docs/reviews/2026-11-25-codex-217-224-audit.md` 第 1 条。

## 问题

`src/zucai/digest_notify.py` 的 `publish()` 在正文超过 65,536 字符时直接报错
（「摘要超过单条 GitHub 评论长度限制；保留数据分支全文，未截断发布」）。这一期日报不发评论、
不更新「每日报告」页，所有者什么都收不到。

- 2026-11-21 的日报已到 64,997 字符，离上限只差 539。
- 2026-11-25 最长一版 50,750 字符，其中排在最后的「技术数据覆盖率」一节占 15,364。
- 日报的二级章节（`## ` 开头）顺序固定：预测、14 场在前，复盘、结算、采集记录在后。

## 范围

1. 正文超过上限时不再报错，改发「缩短版」评论：
   - 首行免责行、唯一的当日标记保持不变；
   - 按日报原有顺序保留能放下的完整二级章节（连同它下面的三级小节），不在章节中间截断；
   - 末尾写明三件事：本期全文超过单条评论上限、被省略的章节标题清单、数据分支上全文的链接
     （`daily/<日期>/<版本>.md`）。
2. 数据分支归档的全文不变：不截断、不改哈希。
3. 回执（`<版本>.notification.json`）仍能对应到它代表的归档版本：记下实际发出的正文哈希，并标明是缩短版。
   后续班次选「上一版」、同日评论的替换规则（`_deliver_comment`）在缩短版下与全文版行为一致。
4. 「每日报告」页正文（`monthly_issue_body`）嵌入最新日报时，放不下先用缩短版，仍放不下才退回只放链接。
5. 补发（`redeliver`）走同一规则。
6. 同步 `docs/ARCHITECTURE.md` 的日报通知一节。

## 不做

- 不删减、不改写日报任何章节的内容，不调整章节顺序。
- 不改数据分支的归档格式。
- 不动「每日报告」页的目录格式（那是 T81）。

## 验收标准

1. 离线测试：70,000 字符的日报样本 → 发出的评论不超过 65,536 字符，含免责行、唯一标记、省略章节清单和全文链接；
   保留下来的章节与原文逐字相同。
2. 离线测试：正好 65,536 字符 → 发全文；65,537 字符 → 发缩短版。
3. 离线测试：第一个章节本身就放不下 → 仍发出只含说明和全文链接的评论，不报错。
4. 离线测试：缩短版发出后写入回执；同一版本重试不重复发评论；下一班的全文版能替换同一天的评论。
5. 现有 `digest_notify` 相关测试全绿。
6. 合并后验收（Claude）：正式运行里正常长度的日报照常发布。超长这条路在真实出现超长日报之前只有离线测试，
   验收回执里照实写明，出现后补验。
