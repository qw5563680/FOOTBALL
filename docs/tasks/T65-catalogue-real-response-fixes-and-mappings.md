## 范围

### 一、API-Football 目录解析：坏赛季不得拒收整份目录

1. 单个赛季的起止日期无效（起始晚于结束、明显越界年份等）时，保留该联赛与该赛季年份，
   日期置空并在该赛季上记原因；目录整体照常入库，`summary.json` 把这类问题列为警告并给出联赛 id、
   赛季与原值。结构性错误（缺字段、重复 id、非 JSON 等）仍然整份拒收。
2. 从已归档原件裁剪真实样本进 `data/fixtures/`（含 id 271 那一条与若干正常条目，几十 KB 以内，
   写明来源提交与哈希），替换或补充现有合成样本。
3. 修复合并后由审查者重新触发一次目录探测，产出 `apif` 指针。

### 二、竞彩全年目录解析：接受真实空页

1. 真实空页（`resultCount=0`、`pages=0`、带 `leagueList`）记为「当天无赛果」，不计失败；
   其余异常形状仍报错。用已归档的真实空页裁剪样本补测试。
2. 把 `leagueList` 作为官方赛事字典单独入档（id、简称、全称、首次观察运行），不导入比赛。
3. 已归档的 406 页原件足以离线重算，不需要重新请求竞彩；提供离线重算入口或在下次探测时生效均可，
   在 PR 写明选择。

### 三、总表名称与竞彩官方名称的对照

1. 在 `data/league_map.json` 的 90 行上增加官方 `leagueId` 与官方简称、全称的对照，
   每行给证据（官方全称、总表「来源出现过的名称」、两边的场数与日期范围）。
   只有名称不同、全称指向同一赛事的行可以提案为已核准；总表一行对应多个官方赛事或反过来的
   （升降级附加赛、世预赛各赛区、日职与百年构想联赛、官方的「杯赛」「国际赛」等）保持候选并列出理由。
2. 对照不得用模糊匹配自动核准；逐行由审查者对照原件确认。
3. 对照完成后重算交叉核对，输出真正需要所有者决定的清单（预期远少于现在的 65 项）。

### 四、69 个候选赛事的接口映射提案

1. 用已归档的真实 `/leagues` 原件，为总表第 3 至 8 组的每个候选赛事提案 API-Football 映射：
   联赛 id、名称、国家、类型、目录列出的赛季，状态先为候选，证据写全；审查者核对后在同一 PR 内
   由实现者改为已核准。目录里找不到的赛事写明查过的名称，不写成「接口无」之外的结论。
