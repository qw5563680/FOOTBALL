# T91 工作流把 GitHub 的接口次数用光：实验模型时好时坏、日报偶尔发不出去

来源：2026-11-25 Claude 排查 T88 实测运行时发现；所有者当天说「写 T91」。
同时回答了 `docs/reviews/2026-11-25-codex-217-224-audit.md`「遗留」第一条（日报四次返回 403，原因未查明）。

## 问题

GitHub 给工作流令牌的接口调用次数是每个仓库每小时 1000 次。用光以后，后面所有调用都返回 403
（`API rate limit exceeded for installation`），到整点后才恢复。

已核实的事实：

| 现象 | 证据 |
| --- | --- |
| 实验模型失败（「实验数据恢复或计算失败」） | 运行 45271742315、45398126533、45479530916、45604107484 的 predict 日志里，报错都是 `ReleaseHttpError: Release HTTP 403 … API rate limit exceeded for installation` |
| 日报发不出去（「摘要未推送：GitHub HTTP 403」） | 运行 44719333831、44788335397、44893137252、45048943753：四次都是 predict 先报次数用光，约 3 分钟后 digest 返回 403 |
| 次数为什么用得快 | `src/zucai/stats_release.py` 的 `download()` 每下载一个文件都调用一次 `_assets()`，把整个 Release 的文件清单分页重列一遍。`stats-raw-202611` 这个 Release 有 700 多个文件，列一遍至少 8 次调用 |

日报那四次失败，日志里没有打印 GitHub 的响应正文，所以「是同一个原因」是由时间先后推出来的，四次无一例外。

## 范围

1. 同一次运行里，每个 Release 的文件清单只列一次，后面的下载、核对都用这一份（有新上传时只更新这一份，不重列）。
2. 所有调用 GitHub 接口的地方（Release 上传下载、日报评论、置顶、Issue 更新）在收到「次数用光」的 403 或 429 时，
   读响应头里的恢复时间：
   - 等得起（在所在步骤的时间预算以内）就等到恢复再继续；
   - 等不起就明确报「GitHub 接口次数用光，几点恢复」，不当成普通失败，也不重试刷请求。
3. 日报推送排在最优先：一班里先保证日报评论能发出去。日报这一步遇到次数用光时，等到恢复后补发，不直接判失败。
4. 每个 job 结束时在 job summary 写一行：这一步用了多少次 GitHub 接口、还剩多少、几点恢复。
5. 日报推送失败时把 GitHub 返回的状态码和原因类别（次数用光 / 权限不足 / 其他）写进日志，不打印令牌。
6. 同步 `docs/ARCHITECTURE.md`。

## 不做

- 不改任何模型、训练和预测内容。
- 不减少技术数据的采集范围，不删 Release 里的文件。
- 不换成个人令牌或别的凭证来绕开次数限制；凭证方面的任何改动须所有者决定。
- 不新增对体育数据源的请求。

## 验收标准

1. 离线测试：一次运行里下载 50 个文件，列清单的调用只有 1 轮（按分页数计），不是 50 轮。
2. 离线测试：收到次数用光的 403，恢复时间在预算内 → 等待后成功；在预算外 → 报出明确原因和恢复时间，不重试。
3. 离线测试：日报推送遇到次数用光 → 等到恢复后发出，回执照常写入。
4. 离线测试：日志和 summary 里没有令牌。
5. 现有测试全绿。
6. 合并后验收（Claude）：连续 3 天的正式运行里，predict 和 digest 的日志没有 `API rate limit exceeded`；
   job summary 有接口次数一行；实验模型不再因为这个原因失败。期间如果仍然出现，如实记录出现在哪一步、用了多少次。
