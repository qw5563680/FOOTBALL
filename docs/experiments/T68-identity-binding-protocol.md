## 1. 目标、现状与设计选择

让新核准赛事的接口球队有可追溯的项目身份，已售竞彩比赛能与历史数据一一关联，然后逐赛事开启每日采集。
保留原始来源行、可靠赛果与已有关系；修正来源重复计数，不改被冻结的预测、旧报告、旧评分或账本。
不建 T62 模型、不改参数或模型来源清单、不新增体育请求，不把赛后核验说成当时赛前已知。

## 2. 输入冻结与证据来源

### 2.1 三类主证据

1. **库内竞彩场次**：`jc:<matchId>`、原始竞彩主客队 ID、唯一项目球队 ID、竞彩赛事 ID、开球 UTC、90 分钟赛果。
   库内字段不是自证：从赛程归档、赛果原件及明确核准别名找到来源指针；同名球队不能仅靠 `Team.name` 获得授权。
2. **12 个月官方目录**：`state/catalogue/43539673769-1/jc/`，窗口为北京时间 2025-11-01 至 2026-10-31。
   用 `matchId`、`leagueId`、`homeTeamId/awayTeamId`、全称/简称、`sectionsNo999` 核对赛果和开售覆盖。
   这不是完整赛程，未开售比赛不在其中；`matchDate` 不保证是开球北京时间，不能拼成 00:00 来匹配。
3. **T61 已回填接口历史**：四个运行 `43565204451-1`、`43572899357-1`、`43577639890-1`、`43583697515-1` 的
   `state/catalogue/<run>/backfill/api-football/2026-11-14/fixtures_*.json` 及 sidecar，连同已入库行与拒收/暂缓记录。
   数据提交有 728 份 fixtures 原件（文件数不是不重复赛季数，也不是成功入库数）；回填报告文件不当作 fixtures。
   被暂缓的比赛仍从原件参加唯一性检查，不能只用入库成功子集。

必要的辅助证据只复用已有归档：同一竞彩 ID 的赛程、已有正式 APIF 别名的批准来源、
`data/api_football/nations.json` 和对应欧国联原件、原有 FD 身份/时区证明。
既有联赛早年球队允许以同联赛 FD 场次作主证据：有已核验的时区/准确开球、规范身份，且满足第3节同样的主客、90分钟比分与双向唯一条件。英文名相同不构成授权；FD 也无证据的保留临时身份。
`international_results`、赔率、排名、译名相似度均不作为球队身份授权。

### 2.2 原件与时间的检查

- 固定代码 SHA、数据 SHA、正式别名 SHA、注册表 SHA、原件 SHA；只在新的副本上分析。
- 校验 HTTP 状态、URL/请求赛事与赛季、分页完整性、sidecar 哈希、带时区的实际 `fetched_at_utc`。
  缺元数据、坏哈希、未完成分页或无法解释的重复 fixture ID 都不能宣称完整。
- 完整性指对应赛事/时段的**所有竞争行**都在检查中，含未完赛、取消、拒收和未入库行。
  不能先按比分、已绑定球队或“能解析的行”删掉竞争者，再宣称唯一。
- 原始捕获时间、提出候选时间、批准时间、实际应用/核验时间分别保存，展示同时给 UTC 与 `Asia/Shanghai`。
  身份与关系最早生效界不早于实际批准和应用核验；不把今日新确认的身份倒填到旧 raw 的捕获日期。
- 缺竞彩精确时间时，先以同一 `jc:<matchId>` 查已有赛程原件或有来源的库内行。仍缺则记录
  `missing_jc_kickoff_evidence`，不提案。需要新原件时列出 ID/日期/所缺字段，由审查者在 Actions 按配额取得；开发环境不调用正式 key。

### 2.3 正式前置步骤：补齐目录比赛开球时刻（A 段）

库内时刻只有来源身份、主客体彩编号和北京日期均可复核才跳过；疑点单列，不从API借时间。

## 3. 一条新绑定什么时候可以提案

绑定的业务键是 `(provider=apif, provider_competition_id, provider_team_id)`，目标是唯一项目规范身份。
规范中文名是展示值，源数字 ID 与球队类别才是身份边界。

### 3.1 必须同时满足的逐场条件

1. **同一赛事**：已有核准的一对一赛事映射，或第 6 节已核准的逐场赛事归属；仅中文同名不够。
   泛称赛事的候选可以进入人工待核清单，但归属未核准不能成为绑定依据。
2. **准确开球时间一致**：两份独立来源时间转换为 UTC 后相等，并记录原始精度；
   分钟来源按其原始 HH:MM:00 表示，若另一来源有非零秒且不相等，仍须人工核对，不截断实际秒值来制造一致。
   只有日期、默认午夜、已知占位时钟均不合格。
   不使用 ±3 小时放宽此条件，三小时只保留为竞争者/导入保护窗口。
3. **主客方向一致**：APIF 主队 ID 对竞彩主队规范身份、客队同理；中立场也保留来源指定方向，不能调换以凑比分。
4. **双方已结束且 90 分钟比分一致**：90 分钟含补时、不含加时及点球；复用现有解析器的 `regular_time_basis`。
   AET/PEN 只有能明确拆出常规时间时可用，保存拆分字段及算法依据；只有总比分、判罚 AWD/WO、腰斩或缺赛果均待核。
   `sectionsNo999` 仍需通过竞彩赛果口径检查，不把 `winFlag`、让球或赔率当实际比分。
5. **双向唯一**：在完整赛事资料与原始三小时竞争窗口内，保留所有方向兼容的竞争比赛；先判断唯一，再核对比分。
   APIF 候选只对应一个竞彩实体，竞彩实体也只对应一个 APIF fixture；已有同场多来源先按已核准关系去重为实体。
   一场匹配到两个对手、同队近时多场、来源 ID 已被占用或反向冲突，不靠比分选中其中一个。
6. **身份类型与目标唯一**：项目队 ID 必须唯一存在，或能从明确竞彩数字 ID 创建独立规范身份的方案已被逐条批准。
   同一 APIF ID 全局不能绑定两个不同规范球队；同一赛事同一规范球队不能有两个生效 APIF ID。
   有冲突就撤下相关提案，不采取先处理者胜出的策略。

最小逐场证据可以是一组满足以上全部条件的完赛对照，主客各形成一条提案；
没有已绑定对手时也不得靠中文名自举，必须有完整窗口的双向唯一证据，审查者逐条确认。
允许同一个 PR 分层提案：每条记录 `layer` 与 `depends_on`（前层候选的稳定ID）。本层仅用正式锚及上一轮已验证结果，不能同轮循环自证；
前层任一被否/冲突，其直接与传递依赖一并撤下。候选仍不是生产生效别名，整条依赖链经审查逐层核准后才可应用。
比分只是确认或否决已有唯一对照，不能用于搜索同场或消除歧义。

### 3.2 候选内容与审批

继续使用 `state/alias_candidates/apif.json` 的按赛事/球队 ID 组织方式。
T68 项保持 `status=proposed`，另注明 `evidence_status=strict_verified` 或待核原因；
“算法验证”不直接写正式表的 `auto_verified`，也不让导入器读取待审队列。

每条提案至少带以下信息（字段可在实现中沿用现有命名，但信息不得省略）：

| 类别 | 必需信息 |
| --- | --- |
| 身份 | APIF 赛事/球队 ID，来源名，球队类别；目标规范名及基线队 ID；竞彩球队 ID；适用赛事和年份/阶段范围 |
| 逐场证据 | 两边 match ID、原始赛事名/ID、同向主客数字 ID、原始时间/精度、UTC/北京时间、90 分钟比分及口径 |
| 唯一性 | 时段覆盖、竞争 ID 全集、候选数、已有同场关系、拒收/暂缓行是否完整纳入、冲突检查结果 |
| 来源 | 数据提交、原件/sidecar 路径与 SHA、JSON 指针或行号、真实捕获时间；同源传播时加原批准条目指针与 SHA |
| 治理 | 协议版本、提案时间、核验时间、人工待核理由；批准后才填写真实 `approved_by/approved_utc/approval_pr` |

同一提案重复生成不新增候选、不重写首次证据；新证据追加，互相矛盾的证据全部保留并阻止生效。
仅通过 PR 修改 `data/team_aliases/api_football.json` 生效，由 Claude 逐条核对、所有者最终合并。
未知规范中文名不由代码音译或猜测；可先留空进入人工清单，未核准不创建正式队。

## 4. 跨赛事身份复用与球队类别

### 4.1 俱乐部

同一个 APIF 数字球队 ID 已在本国联赛正式核准，可向杯赛/洲际赛事**提出同源传播候选**，条件是：

- 源条目是正式 active 条目，有完整原始证据或批准来源；库内 `apif:<league>:team:<id>` 单独存在不能替代授权。
- 原件证明目标赛事确有该数字 ID，源/目标均是同一国家/足协体系下的同一俱乐部实体，成年/性别/一线或预备属性一致。
  洲际赛 `country=World` 不能证明球队国别，未知属性不得按“默认成年男足”填充。
- 全部正式表、国家队注册表、数据库占用检查无跨赛事 ID 冲突、同规范名多 ID、旧 proposed 冲突或身份类别矛盾。
- 目标杯赛仍单独落正式别名条目，保留 `same_provider_id` 来源赛事、源文件 SHA、原批准指针和目标原件；
  不把整个联赛别名表无条件复制到所有杯赛。

同源传播是在复用已有核准身份，不是从目标杯赛重新推断球队。
若原身份缺证、换 ID、俱乐部重组或预备队与一线队边界不清，则退回第 3 节逐场证据/人工核验。
实现不简单扩大 `cup_identity.CUP_LEAGUES`，也不在新赛事中启用其无比分运行时自动认队路径。

### 4.2 国家队

成年男足可以复用 `data/api_football/nations.json` 中欧国联已核准的同一 APIF ID，
须能追溯该注册表版本、原欧国联证据与唯一项目队 ID，且目标赛事/原件明确为成年男足。
欧国联注册表本轮不改；新赛事仍经候选与正式 APIF 别名 PR 核准。没有欧国联身份的国家队走第 3 节。

球队类型至少区分 `club/senior/reserve`、`national/senior/U23/U21/U20`、`men/women`，
奥运/亚运代表队另加独立 `olympic/asian_games` 身份范围，即使国名或人员相同也不并入成年队。
女足国家队、青年国家队、同国俱乐部和成年男足不得共用项目 ID。
需要独立规范中文名时保留年龄/性别/代表队限定；全球名称索引若会撞到成年队，应拒绝并交人工定名，不能去掉限定词。

类别证据取已核准注册表、明确赛事类别及可核验的球队原件。名称中的 U21/Women/II 可以触发拒绝检查，
但“名称没有这些词”不是成年一线队的正面证据。ID 相同但类别矛盾也要停，不把数字 ID 当万能授权。
国家队泛称 `国际赛` 本身不能证明是成年男足；不得通过扩展 `NATIONAL_TEAM_COMPETITIONS` 把所有泛称场次批量并入。

### 4.3 存量合并必须受目标范围约束

现有 `apif_reconcile` 存在“同源 ID 在任一正式联赛生效，便扫描其他联赛历史”的传播能力。
T68 新核准 ID 只允许在该 PR 明列并已落地正式别名的目标赛事/类别/年份范围内应用。
不授权它越过范围处理同 ID 的青年、女足或未分类赛事；实现时加范围检查与回归测试，旧批准条目保持既有语义。
历史队的目标原本不存在时，先按已批准计划创建一个唯一规范目标，再通过既有 reconcile 移动引用；
不得为了通过检查把临时球队直接改名成碰巧存在的成年队。

## 5. 回放、迁移与不可变边界

验收覆盖两种先后顺序、原比分不改、关系导出恢复和再次0新增；不把关系回放说成旧预测已使用新身份。

- 普通同联赛、规范双边 ID 已知的关系，复用现有三小时唯一性检查和 T63 时标证明；不重写原可靠赛果。

- 副本验收前后记录冻结目录、所有既有预测、记分板与账本的路径清单及 SHA256；导出恢复还要比较关系、候选、审计与训练选择。
  不能仅比较 SQLite 文件哈希代替各表逻辑比较，也不能仅以“程序退出 0”证明关联正确。

## 8. 第五节增补的具体处理

### 8.1 36 小时跨来源重叠：隔离不等于认定同场

沿用 `source_result_quarantine.pending_fd_identity_overlaps` 的读时隔离机制，但**不是只改 3 为 36**：
当前代码仅接受一侧 FD 身份缺失，恰好会漏掉本次双方 ID 已经相同的 12 组。
新增“同联赛、同向规范主客 ID、差 ≤36 小时、跨来源而无已核准同场关系”的待核分支，
保留原单侧未知保护；绑定前后都重新扫描。付费来源 APIF（以及 T63 已有的 FDORG 付费扩展来源）
与 JC/FD 等另一来源发生该风险时不能重复进入训练；多候选只会扩大隔离/审计，不能因不唯一而放过。

- 不要求比分相同才隔离；比分不同同样可能是更正/判罚/错日期。比分只展示给人工核对。
- 使用训练截点可知的结果与身份：沿用 T63 的两侧赛果都已通过可知性筛选时隔离新增付费行，
  保留原可靠来源；不能借今日才出现的对照修改过去的冻结训练选择。
- 同一组件里即使已有第三来源证明，也须检查这两个实体是否已真正连通；不能因为某行“有任何关联”便免检。
  对两条都属新增付费来源而无可靠旧源的冲突，均暂缓，等待明确决定，不能随机保留先到一条。
